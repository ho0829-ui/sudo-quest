## 0. 지켜야 할 전제

- **로그인 없이도 게임은 그대로 된다.** CLAUDE.md 2절("정적 사이트로 GitHub Pages에서 동작")을 지키려고, 로그인은 *선택 기능*으로 얹는다. 백엔드가 꺼져 있거나 정적 배포만 있을 때도 실습·캠퍼스·파티·엔딩은 지금처럼 브라우저 저장소로 동작해야 한다.
- **비밀값은 사용자가 직접 넣는다.** Google OAuth 클라이언트 비밀은 `backend/.env`에만 둔다. `VITE_*`·브라우저 코드·문서에 넣지 않는다(기존 규칙 그대로).
- **런타임 라이브러리를 늘리지 않는 쪽을 우선한다.** 프론트 런타임은 react·react-dom만, 백엔드는 이미 있는 `requests`·표준 라이브러리로 OAuth를 구현하는 안을 기본으로 한다(아래 1-2). 새 패키지가 꼭 필요하면 이유를 먼저 설명하고 묻는다.
- **게임 명령은 계속 가상 상태만 바꾼다.** 로그인·튜토리얼은 UI·백엔드 쪽 일이고 엔진 규칙은 그대로다.

## 1. Google 로그인(SSO) · 회원가입

### 1-1. 로그인하면 무엇이 달라지나 (제안)

| 기능 | 로그인 전(지금) | 로그인 후 |
|---|---|---|
| 실습 진행·최고 점수 | 이 브라우저 저장소 | 계정에 저장 → 다른 기기에서도 이어짐(처음 로그인 때 브라우저 기록과 합침) |
| 운영자 등급·파티·피날레 본 기록 | 브라우저 | 계정 |
| 게시판 글·댓글 | 닉네임 + 선택 삭제 비밀번호 | 계정 닉네임으로 쓰고, 비밀번호 없이 내 글 삭제 |
| 튜토리얼 | 없음 | 첫 로그인 때 한 번(2절) |
| 소리·모션 설정 | 브라우저 | 브라우저(기기마다 다른 게 자연스러워 그대로) |

"회원가입"은 따로 화면을 두지 않고, **처음 Google로 로그인하면 계정이 생기고 닉네임만 정하는** 방식(가입 = 첫 로그인)을 제안한다.

### 1-2. 방식 — 추천: 백엔드가 처리하는 Authorization Code + PKCE

| 방식 | 장점 | 단점 |
|---|---|---|
| **A. 백엔드 OAuth(추천)** — FastAPI가 Google로 보내고(`/api/auth/google/start`), 돌아오면(`/callback`) 코드 → 토큰 교환 | 프론트에 Google 스크립트·라이브러리 없음, 비밀은 서버에만, 세션을 httpOnly 쿠키로 안전하게 | 백엔드가 HTTPS로 배포돼 있어야 실제 사용 가능(개발 중엔 localhost 허용) |
| B. Google Identity Services 버튼(프론트) + 백엔드가 ID 토큰 검증 | 버튼이 익숙함, 구현 짧음 | 외부 스크립트(accounts.google.com) 추가, 서명 검증에 새 백엔드 패키지가 필요할 가능성 |
| C. Firebase Auth·Supabase 같은 관리형 | 가장 빠름 | 외부 SDK·서비스 종속, 게시판 SQLite와 계정이 따로 놂 |

A를 고르는 이유: 지금 구조(게시판 FastAPI + SQLite)에 그대로 붙고, 새 런타임 의존성 없이 갈 수 있다. ID 토큰은 Google 토큰 엔드포인트에서 TLS로 직접 받으므로 OIDC 규격상 서명 검증을 생략할 수 있고, 대신 `iss`·`aud`·`exp`·`nonce`를 검사한다.

### 1-3. 흐름

1. 레일(왼쪽 메뉴) 위 "Google로 로그인" → `GET /api/auth/google/start`: `state`·`nonce`·PKCE `code_verifier`를 만들어 짧은 수명의 서명 쿠키에 담고 Google 동의 화면으로 보냄(scope `openid email profile` 중 **최소한**만).
2. `GET /api/auth/google/callback?code&state`: state 확인 → 코드 교환(`requests`) → ID 토큰의 `sub`로 계정 찾기/만들기 → 세션 쿠키(`HttpOnly; Secure; SameSite=Lax`, 30일) → 게임으로 되돌림.
3. 처음이면 닉네임 정하기 화면(게시판 닉네임 규칙 재사용) → 튜토리얼(2절).
4. `GET /api/auth/me`(내 정보), `POST /api/auth/logout`, `DELETE /api/auth/me`(**탈퇴: 계정·세션·진행 기록 삭제**, 내 게시글은 "탈퇴한 운영자"로 남길지 지울지 결정 필요).

### 1-4. 저장(게시판 SQLite에 스키마 v4)

- `users`: id, google_sub(유일), nickname, created_at, tutorial_done_at, (email은 **저장하지 않는 것**을 기본 제안 — 쓰지 않으면 들고 있지 않는다)
- `sessions`: 세션 ID의 **해시**, user_id, expires_at, created_at (쿠키 원문은 저장하지 않음)
- `progress`: user_id, scenario_id, best_score, cleared_at (브라우저 `incident-game/v1`과 같은 모양)
- `posts`/`comments`에 user_id(선택) 열 추가 — 로그인 글은 비밀번호 없이 본인 삭제

### 1-5. 보안·개인정보 체크리스트

- state·nonce·PKCE, 리다이렉트 URI 정확히 일치, 쓰기 요청은 기존 Origin 검사 + SameSite 쿠키
- 세션 만료·로그아웃 시 서버에서 무효화, 로그인 시도·쓰기 속도 제한(기존 게시판 제한 재사용)
- 개인정보 처리 안내(수집 항목: Google 계정 고유번호·닉네임·학습 기록, 목적, 보관 기간, 탈퇴 방법) — 공개 배포 전 필수
- 코치 요청에는 지금처럼 정답 정보·계정 정보를 보내지 않음

### 1-6. 테스트

- 백엔드: Google 토큰 엔드포인트를 가짜로 바꿔 콜백 성공·state 불일치·aud 불일치·만료 토큰·재사용 코드, 세션 만료·로그아웃·탈퇴, 진행 기록 합치기(브라우저와 서버 중 높은 점수)
- 프론트: 로그인 안 했을 때 지금 화면과 동일, 로그인 후 레일 표시, 서버 꺼짐 시 브라우저 저장소로 계속

## 2. 첫 로그인 튜토리얼

### 2-1. 무엇을 배우게 할까

게임의 사고 흐름(증상 확인 → 범위 좁히기 → 가설 → 검증 → 조치 → 재발 방지)을 **5분 안에 직접 해 보게** 한다. 설명 슬라이드가 아니라 진짜 터미널을 쓰는 연습 실습이다.

1. 캠퍼스: "방 = 분야, 경보등 = 아직 안 푼 실습" (방 하나를 가리키는 말풍선)
2. 브리핑: 티켓에는 **증상만** 있다는 것
3. 터미널: `help` → `ls` → `cat` 하나씩 쳐 보기, ↑ 기록·Tab 자동완성
4. 조사 현황·힌트(점수가 깎인다는 것)·AI 코치(정답은 안 알려 준다는 것)
5. 원인 제출 → 틀려도 괜찮음 → 조치 → 리포트(포스트모템 4가지)
6. 끝: "다음 실습 시작" 버튼으로 실제 1번 실습

### 2-2. 만드는 방법(제안)

- **튜토리얼 전용 아주 쉬운 시나리오 1개**를 `src/scenarios/`에 데이터로 추가(엔진 수정 없이 — CLAUDE.md 4-3). 점수·기록·파티 계산에서는 제외(`tutorial: true` 같은 표시 → 시나리오 타입에 선택 필드 1개, 자동 검증 테스트는 그대로 통과해야 함).
- 화면 위 **코치 마크**(해당 요소를 밝히고 나머지를 어둡게, 말풍선 + 다음/건너뛰기) 컴포넌트 하나. 각 단계는 "이 명령을 실제로 쳤다" 같은 **조건을 만족해야 다음으로** 넘어감.
- 안내 캐릭터는 기존 분야별 NPC(퀘스트 브리핑) 중 한 명을 재사용.
- 언제 나오나: 계정의 `tutorial_done_at`이 비어 있는 첫 로그인. 로그인 안 한 사람에게도 레일/도움말에 "튜토리얼 다시 하기"로 열어 둠(브라우저 저장소 표시).
- 건너뛰기·다시 하기, 모션 끔·동작 줄이기·키보드·좁은 화면 대응.

### 2-3. 테스트

튜토리얼 시나리오 자동 검증(풀이 경로), 단계 조건(명령을 치기 전에는 다음으로 안 넘어감), 건너뛰기 후 다시 안 뜸, 점수·기록·파티에 포함되지 않음.

## 3. 배포

### 3-1. 지금 상태 (확인한 사실)

- `.github/workflows/deploy.yml`: 테스트 → 빌드 → GitHub Pages 배포. **`main` 브랜치 push에만 배포**한다. 지금 작업은 `feature/sudo-quest`, 기본 브랜치는 `master`라 이대로는 배포되지 않는다.
- 프론트는 `/api/...` 상대 주소로 백엔드를 부르고 개발 중엔 Vite 프록시가 넘겨 준다. **정적 배포(Pages)에서는 `/api`가 없으므로** 백엔드 주소 설정(`VITE_API_BASE` 같은 공개 설정 — 비밀 아님)이 필요하다. 백엔드가 없으면 지금처럼 "코치 오프라인·게시판 준비 중"으로 우아하게 동작.
- 백엔드는 FastAPI + 게시판 SQLite + Chroma 색인 + LLM 호출(유료 키). 배포하려면 디스크가 유지되는 서버가 필요하다.

### 3-2. 구성 — 추천

```
https://<도메인>          → 프론트(정적)      GitHub Pages (커스텀 도메인)
https://api.<도메인>      → 백엔드(FastAPI)   디스크가 유지되는 작은 서버/컨테이너
```

- **같은 상위 도메인**을 쓰는 이유: 로그인 세션 쿠키가 "같은 사이트"로 취급돼 브라우저의 제3자 쿠키 차단에 걸리지 않는다. `github.io` 주소 + 다른 도메인 백엔드 조합은 로그인 쿠키가 막힐 수 있다.
- 백엔드 호스팅 후보(결정 필요): Fly.io·Render·Railway(볼륨 붙는 컨테이너), 또는 작은 VPS. SQLite·Chroma 파일이 있어 **영구 디스크**가 필수.
- Google OAuth 리다이렉트 URI: `https://api.<도메인>/api/auth/google/callback`(운영)·`http://localhost:8000/...`(개발)을 Google Cloud 콘솔에 등록(사용자가 직접).

### 3-3. 해야 할 일 목록

1. 배포 브랜치 정리: `feature/sudo-quest` → `master`(또는 `main`) 병합 여부와 워크플로 대상 브랜치 맞추기(사용자 결정).
2. 프론트: API 주소 설정, 백엔드 없을 때 동작 유지 확인, Pages 커스텀 도메인·HTTPS.
3. 백엔드: 실행 이미지(Dockerfile)·헬스 체크·`CORS_ORIGINS`/쿠키 도메인·HTTPS·환경변수(키는 호스팅의 비밀 저장소에 사용자가 입력).
4. 데이터: SQLite·Chroma 백업(하루 1회 스냅숏), 시드 예시 글은 운영 DB에 넣을지 결정.
5. 비용·남용 방지: 공개되면 코치(LLM) 호출이 비용이 된다 → 로그인 사용자만 코치 사용, 계정·IP별 일일 한도, 응답 캐시(이미 있음), 월 예산 알림. 게시판 운영자 키(`COMMUNITY_ADMIN_KEY`) 설정.
6. 운영: 오류 로그 확인 방법, 배포 후 점검 목록(실습 24개 자동 검증은 CI가 이미 함 + 로그인·게시판·코치 수동 점검).

## 5. 결정할 것 (사용자)

1. **로그인 방식**: A(백엔드 OAuth, 추천) / B(Google 버튼) / C(관리형 서비스)
2. **로그인이 필요한 기능**: 게시판 글쓰기·코치를 로그인 사용자만? (공개 배포 시 비용·스팸 때문에 코치는 로그인 전용을 추천)
3. **이메일 저장 여부**: 저장 안 함(추천) / 저장(연락용)
4. **탈퇴 시 게시글**: "탈퇴한 운영자"로 남김 / 함께 삭제
5. **도메인**: 구입·사용할 도메인 이름(같은 상위 도메인 구성을 위해 필요)
6. **백엔드 호스팅**: Fly.io·Render·Railway·VPS 중 선택(월 비용 확인 필요)
7. **배포 브랜치**: `master` 병합 시점과 Pages 배포 대상 브랜치
8. **Google Cloud 준비(사용자 작업)**: 프로젝트 생성, OAuth 동의 화면, 클라이언트 ID/비밀 발급 → `backend/.env`에 직접 입력
