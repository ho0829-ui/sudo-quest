# InfraCoach 프로젝트 기획서

작성일: 2026-10-21 · 버전: 0.2 · 상태: 구현 전 설계안

## 1. 프로젝트 개요

**InfraCoach — 가상 장애 실습과 공식 문서 기반 RAG 코칭을 결합한 인프라 장애 대응 학습 서비스**

실제 운영 장애를 경험하기 어려운 학습자가 가상 터미널에서 장애를 조사하고 복구한다. AI 코치는 학습자가 확인한 명령어 출력과 공식 기술 문서를 근거로 다음 점검 방향을 안내한다. 학습자는 복구 이후 자신의 조사 과정과 재발 방지 방안을 검토한다.

단순한 정답 안내보다 ‘관찰 → 가설 → 검증 → 조치 → 복구 확인’ 과정을 훈련한다. 문서가 설명하는 일반적인 가능성과 실습에서 확인한 사실을 구분한다.

## 3. 해결하려는 문제

1. 명령어를 알고 있어도 장애 상황에서 어떤 순서로 확인할지 판단하기 어렵다.
2. 고정된 힌트는 사용자가 이미 확인한 사항과 현재의 오해를 반영하지 못한다.
3. 일반적인 AI 답변은 실제 관찰 기록 없이 원인을 확정하거나 근거 없는 명령을 제안할 수 있다.
4. 실습을 완료해도 자신의 조사 과정과 조치 후 검증이 적절했는지 돌아보기 어렵다.

대상은 Linux·네트워크 기초를 배운 인프라 입문자다. 실제 운영 서버를 자동으로 진단·복구하는 서비스는 이번 범위에 포함하지 않는다.

## 4. 핵심 사용자 흐름

1. 장애 실습 목록에서 환경·난이도·증상으로 실습을 고른다.
2. 장애 티켓을 읽고 가상 터미널에서 명령어를 실행한다.
3. 코치에게 현재 증상 또는 명령어 출력에 관해 질문한다.
4. 코치는 ‘확인된 사실 / 아직 확인하지 못한 가설 / 다음 점검 / 문서 근거’를 제공한다.
5. 사용자가 원인을 제출하고 조치하면 게임 엔진이 복구 여부를 판정한다.
6. 완료 후 실제 수행 기록과 공식 문서를 바탕으로 장애 회고를 확인한다.

별도의 지식 탐색 화면에서는 자연어 조건으로 장애 지식 항목을 검색한다. 모든 지식 항목은 선택·질의응답이 가능하며, 실습이 연결된 항목만 ‘실습 시작’을 제공한다.

## 5. 데이터와 도메인 정의

### 5.1 기본 항목

과제의 ‘항목’은 실행 가능한 게임이 아니라 **독립적으로 선택하고 질문할 수 있는 장애 대응 지식 항목**이다. 약 100건 이상을 확보한다. 이는 아직 수집 완료된 수치가 아니라 첫날 충족해야 할 기준이다.

예: ALB가 생성한 HTTP 503, DNS 이름 해석 실패, 서비스의 로컬 주소 바인딩, 디스크 공간 부족. 하나의 긴 문서 안에서도 독립적인 오류 코드나 문제 해결 절이 있으면 별도 항목으로 만들 수 있다. 동일 내용의 번역·별칭·청크는 새 항목으로 세지 않는다.

기본 속성: ID, 한국어 제목, 원제, 기술 분류, 제품, 증상, 설명, 출처 URL 및 절, 적용 버전, 연결 실습 ID. 근거가 없는 필드는 채우지 않는다. 난이도 등 작성자가 판단한 필드는 작성자 분류임을 구분한다.

### 5.2 세 종류의 데이터

| 데이터 | 역할 | 보관 위치 |
|---|---|---|
| 지식 항목 메타데이터 | 항목 선택·조건 탐색·필수 근거 | Chroma `knowledge_items` |
| 공식 상세 문서 | 원인 가능성·진단·예방 설명의 근거 | 원문 캐시 및 Chroma `reference_chunks` |
| 실습 이벤트 | 현재 가상 환경에서 관찰된 사실 | 게임 세션; 공용 지식 컬렉션에 적재하지 않음 |

### 5.3 수집 전략

공식 문서의 목차·오류 목록에서 후보 약 120건을 만들고, 중복 및 근거 부족 항목을 제거해 100건 이상을 확보한다. Linux·네트워크·웹·AWS 중 기존 게임과 연결되는 분야를 우선한다. 분야별 개수는 실제 자료를 확인한 후 결정한다.

공식 URL 허용 목록에서 제목·소제목·요약·URL을 수집한 문서 카탈로그를 구성한다. 질문 시에는 검색어로 이 카탈로그를 검색하고, 후보 선별 후 본문을 수집한다. 전체 인터넷 검색은 필수가 아니다. 수집 가능한 출처를 서비스 화면에 표시한다.

수집 전에 출처별 이용 조건·접근 규칙을 확인한다. URL, 절, 문서 버전, 수집일, 이용 조건 확인 기록, 본문 해시를 남긴다. 영문 원문은 보존하고 한국어 검색용 제목·요약을 별도로 둔다.

### 5.4 근거가 필요한 질문

- ALB에서 모든 타깃이 unhealthy이면 항상 503이 발생하는가?
- 외부에서만 접속되지 않는 현상을 방화벽 문제라고 확정할 수 있는가?
- 파일을 삭제했는데 디스크 공간이 즉시 반환되지 않을 수 있는가?
- 명령 실행이 성공한 사실만으로 서비스 복구를 판정해도 되는가?

교육 서비스이며 실제 시스템에 대한 운영 지시를 대신하지 않는다. 실제 금융·건강 조언 도메인은 아니지만, 가상 환경의 단순화 및 문서 적용 버전은 명시한다.

### 5.5 ‘근거 없이 답하면 무엇이 문제인가’에 대한 도메인 선정 근거

본 서비스는 인프라 장애의 원인과 조치를 다루므로, 같은 증상에 대한 다른 원인이나 제품별 동작 조건을 생략하면 잘못된 진단을 학습하게 된다. 가상 환경에서는 잘못된 학습·불필요한 조치·장애 조사 실패가 직접적인 문제다. 이 지식을 실제 운영에 옮기면 서비스 중단을 늘리거나 불필요한 설정 변경으로 이어질 가능성이 있다. 본 프로젝트에서 실제 운영 피해를 측정했다고 주장하지 않는다.

| 질문 | 근거 없는 답변의 문제 | 필요한 근거 |
|---|---|---|
| ALB 타깃이 모두 unhealthy이면 항상 503인가? | 제품의 fail-open 동작을 누락한 잘못된 장애 모델을 학습 | AWS 공식 헬스체크·오류 문서와 타깃 상태 관찰 |
| 내부에서는 접속되는데 외부에서는 안 되면 방화벽 때문인가? | 관찰되지 않은 원인을 단정해 잘못된 설정을 바꾸도록 유도 | 바인딩·연결 경로 관련 문서와 실제 리스닝/접속 결과 |
| 디스크 공간이 부족하면 로그를 지우면 되는가? | 보존해야 할 기록과 공간 회수 조건을 확인하지 않은 조치 안내 | 파일·디스크 관련 문서, 사용량·파일 상태 관찰 |
| 재시작 명령이 성공했으면 복구 완료인가? | 명령 성공과 사용자 관점의 정상 응답을 혼동 | 서비스 동작 문서 및 조치 이후 상태·응답 기록 |

따라서 ‘근거 없이 답하면 틀리거나 위험해지는 질문이 성립한다’는 도메인 조건에 부합하는 주제로 판단한다. 다만 이것은 도메인 적합성 판단이며, 항목 100건 확보·이용 조건 확인까지 완료됐다는 뜻은 아니다.

RAG 문서는 일반적인 기술 사실과 점검 절차를 뒷받침하고, 실습 기록은 해당 세션의 관찰 사실을 뒷받침한다. 문서 인용이 있다고 원인 진단이 자동으로 옳아지는 것은 아니다. 고정 해설만 제공한다면 정적 콘텐츠로 충분하지만, 사용자마다 다른 질문·조사 기록·관련 기술 문서를 연결하는 코칭에는 RAG 적용 이유가 있다.

## 6. 핵심 기능과 우선순위

| 우선순위 | 기능 | 완료 기준 |
|---|---|---|
| P0 | 지식 항목 100건 이상 및 두 컬렉션 | 항목마다 연결 문서·출처가 있고 재색인 중복 없음 |
| P0 | 검색어 추출·후보 선별·근거 답변 | 세 프롬프트와 수집·검색 과정 확인 가능 |
| P0 | 항목별 채팅·조건 탐색 | 모든 항목 질의 가능, 조건 미충족 후보 제외 |
| P0 | 게임 RAG 코치 | 공개 관찰 기록만으로 단계별 근거 코칭 |
| P0 | 상태·오류·근거 안내 | 키 누락·빈 색인·검색 실패·미인용 안내 |
| P0 | 기존 게임 연결 및 정확성 점검 | 대표 시나리오 3개에서 실습부터 코칭까지 동작 |
| P1 | 대표 시나리오 3개 세밀화 | 아래 환경 개선과 회귀 검증 완료 |
| P1 | RAG 전후 비교 | 5개 이상 동일 질문 비교표, 가능하면 10~15개 |
| P1 | 수행 기록 기반 회고 | 실제 수행한 조치와 일반 예방 권고 구분 |
| P2 | 새 환경 1개 추가 | P0 완료 후 기존 엔진 확장 비용이 낮은 경우 |
| 이후 | Docker 실습·실제 클라우드·배포 | 3일 로컬 MVP 이후 |

P0는 과제 제출의 기준이다. 게임 상세화를 위해 P0를 생략하지 않는다.

## 7. 게임 환경 개선 계획

기존 13개 시나리오를 기반으로 하되 모두를 이번에 확장하지 않는다. 기존 코드의 가정도 공식 문서와 비교해 검증한다.

| 대표 실습 | 세밀화할 부분 | 검증할 내용 |
|---|---|---|
| 디스크 부족 | 파일별 사용량·서비스 상태·시간순 로그의 일관성, 조치 후 상태 재확인 | 공간 확보와 서비스 정상화가 구분되는지 |
| 외부 접속 실패 | 내부/외부 관찰 지점과 바인딩·필터링의 차이 | 동일 증상만으로 원인을 단정하지 않는지 |
| ALB 타깃 상태 | unhealthy/unused 구분 및 공식 동작과의 정합성 | 기존 ‘모두 unhealthy → 항상 503’ 가정 수정 |

새 환경 후보는 별도 클라이언트와 웹 서버를 구분하는 2호스트 네트워크 실습이다. 엔진 변경이 커지면 차기 범위로 미룬다. Kubernetes/Docker를 이름만 붙여 추가하지 않으며, 상태 모델과 검증 가능한 동작을 갖출 때 확장한다.

## 8. 화면 기획

- **실습 목록:** 환경, 난이도, 증상, 학습 목표, 연결 지식 항목.
- **실습 화면:** 티켓·가상 터미널·현재 선택 지식 항목·코치 패널·인용 문서.
- **지식 탐색:** 자연어 조건 입력·분류 필터·검색 카드·항목별 질의응답.
- **결과 화면:** 기존 복구 결과·명령 기록·회고·근거 문서.
- **데이터 상태:** 항목/청크 개수, 색인·수집 상태, 누락 설정 안내. 프롬프트 전문과 스택 추적은 표시하지 않음.

실습의 특정 장애 정답을 선택 항목 제목이나 문서 제목으로 미리 노출하지 않는다. 실습 진입 시에는 중립적인 주제 항목을 연결하거나 사용자가 질문할 항목을 고르게 한다. 정답 공개는 힌트 단계·완료 여부에 맞춘 별도 정책으로 관리한다.

## 9. 기술 구성

- 기존 React/TypeScript: 화면, 가상 명령 실행, 복구 판정.
- Python/FastAPI: 문서 수집·색인·검색·RAG API. API 키는 서버 환경변수에만 보관.
- LangGraph: `retrieve → generate` 두 노드의 답변 그래프.
- ChromaDB: 항목 및 외부 문서 컬렉션.
- GMS/개인 API: 서버 설정으로 공급자 선택. 임베딩 변경 시 별도 색인 생성.

원본 명세의 Python RAG 구성은 유지한다. React 화면은 F2013 직접 구현 UI 심화에 대응한다. 기존 TypeScript 엔진 활용 및 Streamlit 대체에 대한 수업 운영상 별도 제한이 있는지는 제출 전 확인 필요 사항이다. 원문 명세의 라이브러리 버전을 기준으로 시작하고 실행 가능 여부를 첫날 검증한다.

## 11. 성과 평가와 포트폴리오

평가는 추측 억제, 근거 정확성, 다음 점검의 타당성, 숨겨진 정답 노출 여부에 집중한다. 코치 성능이 향상됐다는 주장은 실제 비교 결과가 있을 때만 사용한다.

포트폴리오에는 ‘공식 문서와 관찰 기록을 분리한 코칭’, ‘상태 기반 시뮬레이터’, ‘문서와 다른 시나리오 가정 수정’, ‘검색 설정 비교’를 설명한다. 가상 실습 개발 경험과 실제 서버 운영 경험을 구분한다.
