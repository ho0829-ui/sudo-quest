# RAG 파이프라인 설계문서 — InfraCoach

작성일 2026-10-21 · 코드 기준: `backend/app/`, `backend/scripts/`, `src/` (커밋 7893f6a 이후)

## 1. 전체 구조

```
[데이터 준비 — 질문 전에 실행]
catalog/shortlist_100.json + annotations_ko.json + sources.json
   └─ scripts.build_catalog ─→ catalog/items.json(100) · documents.json(189)      원문 절 추출 성공 확인
   └─ scripts.build_section_catalog ─→ catalog/section_catalog.json(669절)          외부 후보 검색용
   └─ scripts.prepare_corpus ─→ Chroma: knowledge_items(100) / reference_chunks(221)  + manifest

[질문 처리 — POST /api/chat → job]
질문 ─ 프롬프트1(검색어) ─ 절 카탈로그 키워드 후보 ─ 프롬프트2(선별) ─ 미색인 문서만 수집·청킹·임베딩
      └─ LangGraph:  START → retrieve → generate → END
             retrieve: 선택 항목 메타데이터(항상) + 항목·선별 문서 청크 Top-k → 병합·중복 제거·번호
             generate: 프롬프트3 → 인용 번호 검증 → 실제 인용 근거만 반환
```

## 2. 두 컬렉션과 메타데이터

### 2.1 `knowledge_items` — 항목당 1문서

- ID: `item_id`(예: `linux-errno-ENOSPC`). 같은 ID로 upsert하므로 재색인해도 늘지 않는다.
- 색인 텍스트: 한국어 제목 · 원제 · 제품 · 분류 · 오류 코드 · 증상 · 요약 · 원문 발췌(최대 600자).
  - 원문 발췌(영문)를 넣은 이유: 사용자가 "No space left on device"처럼 원문 메시지로 찾을 때도 걸리게 하기 위해서다.
- 메타데이터: item_id, doc_id(주 문서), title, source_url, `source_type=item_metadata`, product, license, publisher.

### 2.2 `reference_chunks` — 외부 문서 청크

- ID: `item_id:doc_id:본문해시:순번`.
  - 같은 문서를 여러 항목이 써도 항목별 ID가 달라 서로 덮어쓰지 않는다. 예: 헬스체크 문서를 ALB 항목 4개가 공유한다(테스트로 확인).
  - 원문이 바뀌면 해시가 달라져 새 청크가 된다.
- 메타데이터: item_id(검색 범위 필터), doc_id, title, source_url, `source_type=external_document`, product, content_hash, chunk_hash, chunk_index, license, publisher, product_version, fetched_at. 질문 중 수집한 청크는 `origin=query_selected`를 추가로 단다.
- item_id가 빠지면 다른 항목의 문서가 근거에 섞인다. 그래서 검색은 항상 `item_id` 조건을 건다.

### 2.3 색인 정체성(manifest)

`data/<CHROMA_PATH>/manifest.json`에 다음을 기록한다.
- 임베딩 공급자 URL, 모델(`text-embedding-3-large`), 정규화(none), 청크 크기·중복, 차원(3072), corpus_hash.

임베딩 설정이나 청크 설정이 바뀌면 기존 컬렉션을 재사용하지 않고(`index_configuration_changed`) 새 경로에 다시 색인한다. 벡터 캐시는 공급자·모델·정규화로만 나눈다. 그래서 청크 설정을 바꿔도 같은 본문은 다시 임베딩하지 않는다.

## 3. 문서 수집·청킹·색인 흐름

1. **출처 등록**: `sources.json`에 허용 URL·출판자·라이선스·이용 조건 URL을 둔다. 수집기는 등록된 URL만 받는다(`source_not_allowed`).
2. **수집 예절**(NF2006): robots.txt를 확인하고 결과를 캐시한다. 호스트당 최소 1초 간격, 429면 자동 재시도하지 않는다. 리다이렉트는 따르지 않는다. User-Agent는 `InfraCoachLearning/0.1`이다.
3. **원문 캐시**: URL별 HTML과 본문 해시를 저장한다. 해시가 맞지 않으면 `source_cache_corrupt`로 거부한다.
4. **절 추출**: 메뉴·광고를 빼고 해당 절만 뽑는다. 절을 찾지 못하면 전체 본문으로 대체하지 않고 실패한다.
   - curl: 단락 앵커
   - man7: `h2절/오류이름` 단락. 같은 오류 이름이 조건별로 여러 번 나오면 모두 모은다.
   - AWS: 제목 경계
5. **청킹**: `RecursiveCharacterTextSplitter`, 1000자·중복 200자(설정값). 대부분의 절은 짧아서(중앙값 약 100자) 한 청크다.
6. **임베딩·색인**: 32건씩 배치로 처리하고, 본문 해시별 벡터 캐시에 없는 텍스트만 API를 호출한다. 마지막에 manifest를 complete로 표시한다.
7. **재실행**: 기본 청크 ID가 모두 있으면 캐시 적중으로 끝낸다(HTTP 0, 임베딩 0). 질문 중 추가된 청크가 있어도 다시 색인하지 않는다.

### 질문 시점 외부 후보 검색(F2004)

1. 프롬프트 1로 검색어(최대 3개)를 뽑는다.
2. **절 카탈로그**(허용 페이지 8개의 절 669개: 제목·앞부분 요약·제품)에서 검색어 토큰과 겹치는 정도로 상위 8개를 고른다. 항목에 연결된 문서는 항상 후보에 넣는다.
3. 프롬프트 2에 후보의 **제목·요약·제품만** 보여 선별한다. 본문을 받기 전에 버릴 문서를 정해 수집·임베딩을 줄이기 위해서다.
4. 후보 밖 ID는 `invalid_document_selection`으로 거부한다. 항목 자체 문서는 맨 앞에 강제로 넣는다. 추가 문서는 최대 4개다.
5. 선택된 문서 중 이 항목으로 아직 색인되지 않은 것만 절을 추출해 청킹·임베딩·색인한다.
6. 검색어 캐시(항목 + 정규화 검색어 + 카탈로그 버전)가 적중하면 2~4단계를 건너뛴다.

실측 예: "write에서 ENOSPC와 EDQUOT는…"에서 후보 11개 중 3개를 선정했고, `write(2) ERRORS: EDQUOT`를 새로 수집해 인용했다. 같은 질문을 다시 하면 재수집 0회였다.

## 4. 검색 결과 병합과 중복 제거

- 근거 1번은 항상 **선택 항목 메타데이터**다. 검색하지 않고 ID로 가져온다(F2006).
- 외부 청크는 `item_id = 선택 항목` AND `doc_id ∈ 선정 문서` 조건으로 Top-k를 검색한다.
- (출처 URL, 본문 해시)가 같은 청크는 하나로 합친다. 같은 문서라도 서로 다른 절·청크는 남긴다.
- 남은 근거에 1번부터 번호를 붙여 프롬프트 3에 넘긴다. 각 근거에는 source_type(항목 메타데이터/외부 문서)이 붙어 있다.
- 임베딩 유사도에 공통 임계값은 두지 않았다. 판단 기준을 정할 평가 데이터가 부족해서다.

## 5. 프롬프트

전문은 `backend/app/prompts.py`에 있다. 모든 프롬프트는 JSON만 출력하게 하고 pydantic 스키마로 검증한다. 입력 안의 지시문은 데이터로 취급한다(프롬프트 주입 방지).

| 프롬프트 | 역할 | 입력 | 출력 형식 | 검증·실패 처리 |
|---|---|---|---|---|
| 1. `SEARCH` 검색어 추출 | 인프라 공식 문서 검색 도우미. 한국어 질문을 영어 기술 용어·오류 코드로 바꾼다. 관찰하지 않은 원인은 확정하지 않는다. | 항목 메타데이터, 질문, 이전 대화 | `{"queries":["..."]}` (1~3개) | 형식 오류면 항목 원제 + 질문으로 대체하고 화면에 안내 |
| 2. `SELECT` 후보 선별 | 질문에 필요한 후보를 최대 4개 고르고, 후보마다 선정·제외 이유를 쓴다. 다른 제품은 차이를 쓴다. | 질문, 항목, 후보(ID·제목·요약·제품) | `{"selected_ids":[...],"reasons":{...}}` | 후보 밖 ID면 거부, 자체 문서는 강제 포함 |
| 3. `ANSWER` 근거 기반 답변 | evidence만 근거로 쓴다. 모든 주요 주장에 [근거 N]. 근거가 없으면 "문서에서 확인되지 않습니다". 대응을 묻는 질문이면 근거의 조치를 빠짐없이 쓰고 근거에 없는 조치는 쓰지 않는다. | 질문, 항목, 이전 대화, 번호 붙은 근거 | `{"answer","cited_evidence_ids","suggested_checks","warnings"}` | 본문의 번호와 목록이 일치하고 실제로 있어야 한다. 실패하면 1회 재요청 후 `citation_validation_failed` |
| 3'. `COACH` 훈련 모드 | 프롬프트 3의 실습용 변형. 관찰 사실은 [실습 기록 N], 문서는 [근거 N]. 사실/가설/다음 점검을 구분하고, 원인을 단정하지 않고, 힌트 단계를 넘지 않는다. 지원하지 않는 명령은 "(실제 환경 참고)"로 표시한다. | 티켓, 연 힌트, 관찰 기록, 쓸 수 있는 명령, 근거 | `{"answer","cited_evidence_ids","cited_observation_ids","suggested_checks"}` | 두 종류 번호를 모두 검증 |
| 4. `EXPLORE` 조건 판정 | 후보 항목의 공개 메타데이터만으로 조건 충족을 판정한다. 확인할 수 없는 조건(난이도 등)은 따로 적는다. | 조건 문장, 후보 20개 | `{"matches":[{"item_id","reason"}],"unverifiable_conditions":[...]}` | 후보 밖 ID는 거부, 판정 후 명시 조건(제품·코드)으로 재검증 |

과제의 세 프롬프트(검색어·선별·답변)에 조건 탐색 판정용 1개를 더했다. 훈련 모드는 답변 프롬프트의 변형으로 본다.

## 6. 청크 크기·중복·Top-k

| 설정 | 값 | 이유 |
|---|---|---|
| `CHUNK_SIZE` | 1000자 | 오류 설명과 확인 절차를 한 청크에 보존하면서, 긴 ALB 절에서 무관한 내용을 과도하게 섞지 않기 위한 시작값 |
| `CHUNK_OVERLAP` | 200자 | 절 경계에서 조건 문장이 끊기는 것을 완화 |
| `EXTERNAL_TOP_K` | 4(근거 최대 5 = 메타데이터 1 + 외부 4) | 원인·확인·조치·예외를 함께 담되 입력 길이와 지연을 제한 |
| `CANDIDATE_LIMIT` / `MAX_SELECTED_DOCUMENTS` | 8 / 4 | 선별 프롬프트 입력 크기와 질문 중 수집량 제한 |

**바꿨을 때의 차이(실측, `청크_TopK_비교.md`):**

| 비교 | 청크 수 | 핵심 원문 문구 포함(15개 중) | 근거 총 글자 수 |
|---|---|---|---|
| 청크 700 / 1000 / 1400 | 247 / 221 / 214 | 13 / 12 / 13 | 8,007 / 9,886 / 10,626 |
| Top-k 2 / 4 / 6 (청크 1000) | - | 12 / 12 / 13 | 5,711 / 9,886 / 11,666 |

- 차이는 Q1(헬스체크 문서의 fail-open 문장이 청크 경계에 걸림) 하나뿐이었다. 서비스 경로에서는 검색어를 더해 검색하기 때문에 청크 1000·k=4에서도 이 문장을 인용했다. 그래서 **1000/200/4를 유지**한다.
- 모든 설정에서 놓친 문구 2개는 다른 항목의 문서에 있었다. 설정으로는 해결되지 않고 질문 중 수집(F2004)으로 해결된다.
- 답변이 조치를 빠뜨린 문제(Q2·Q3)는 k와 무관했다(근거 청크 안에 조치가 있었음). 그래서 Top-k가 아니라 답변 프롬프트를 고쳤다.

## 7. 근거 표시 방식(F2008)

1. 생성 결과의 본문과 suggested_checks에서 `[근거 N]`을 정규식으로 찾는다.
2. 찾은 번호 집합이 모델이 낸 `cited_evidence_ids`와 같고, 실제로 존재하는 근거 번호인지 검사한다.
3. 통과한 번호의 근거만 `citations`로 반환한다. 화면은 이것만 카드로 그린다(제목 링크 = 원문 절 URL, 유형, 출판자, 라이선스, 근거 본문 펼치기).
4. 인용이 0건이면 본문이 "문서에서 확인되지 않습니다"를 포함해야 한다. 이때 화면에 "답변에 인용된 근거가 없습니다"를 표시한다.
5. 형식 검증은 문장이 근거로 실제 뒷받침된다는 보장이 아니다. 내용 타당성은 F2015 비교에서 따로 평가했다.

## 8. 도메인 특화 기능 — 공개 실습 기록 기반 게임 코치(F2010)

**왜 이렇게 설계했나:**
- 인프라 장애 대응에서 위험한 답은 "관찰하지 않은 원인을 확정하는 답"과 "그 환경에서 실행할 수 없는 명령을 권하는 답"이다.
- 그래서 코치는 플레이어가 **실제로 실행해 본 출력**을 사실의 유일한 근거로 쓴다([실습 기록 N]). 일반 기술 설명은 공식 문서로만 한다([근거 N]).
- 답은 "확인된 사실 / 가설 / 다음 점검"으로 나눈다.

**정답 차단:**
- 프론트의 `buildCoachRequest`가 Session에서 허용 필드만 새로 만든다. 보내는 것은 티켓, 연 힌트, 직접 입력한 명령의 출력(최근 30개, 긴 출력은 앞뒤 보존과 생략 표시), 쓸 수 있는 명령 목록, 무작위 세션 ID다.
- 서버 계약은 추가 필드를 거부한다.
- 숨겨진 "실습↔정답 항목" 연결은 쓰지 않고, 질문과 관찰에서 나온 검색어로 지식 항목을 고른다.
- 13개 시나리오 전부를 대상으로, 정답·보기·풀이·학습 목표·포스트모템·미공개 힌트가 요청에 없는지 자동 테스트한다.

**판정은 엔진이 한다:** 복구 여부는 기존 게임 엔진의 `resolution`이 판정하고, 코치는 판정하지 않는다.

## 9. 겪은 문제와 해결

| 문제 | 원인 | 해결 |
|---|---|---|
| AWS 문서의 대시가 "â"로 깨짐 | charset 없는 응답을 requests가 ISO-8859-1로 해석 | charset이 없으면 UTF-8로 해석하고, 깨진 캐시 3개를 다시 받음 |
| man7 첫 단락에 제목 글자가 섞임 | 절 시작을 `<h2 id>`로 잡음 | `</h2>` 뒤부터 읽음. 테스트 고정값으로 확인 |
| ALB 항목 error_codes가 `http-503-issues` | 후보 목록의 code 필드가 절 이름 | HTTP 상태 코드만 추출. 색인 정체성이 바뀌어 새 경로(chroma-v2)에 재색인 |
| "curl에서", "ENOSPC나"가 필터에 안 걸림 | 한글이 `\w`라 `\b` 경계가 생기지 않음 | 영문·숫자 경계 정규식으로 변경, 테스트 추가 |
| 조건 탐색이 "요청 대기 중"에서 멈춤 | React StrictMode 재마운트 뒤 active 플래그가 false로 남음 | 마운트마다 true로 재설정 |
| 청크 설정만 바꿔도 같은 본문을 다시 임베딩 | 벡터 캐시 키에 청크 설정 포함 | 공급자·모델·정규화로만 키를 만들고 기존 벡터 338개를 이동 |
| 답변이 근거의 조치를 생략(Q2·Q3) | 답변 프롬프트의 "간결하게" 지시 | 조치 누락 금지 규칙 추가 → 9문항 재비교에서 정확 8/8 |
| 테스트 간헐 실패 | 모든 고정 벡터가 같아 Chroma 필터 검색이 결과를 빠뜨림 / 색인 직후 다른 클라이언트로 다시 열 때 HNSW 미반영 | 문서별로 다른 벡터 사용(30회 연속 통과). 재오픈 문제는 근본 해결 안 됨 |
| GMS 일시 오류(502) | 공급자 측 | 자동 재시도 0회 정책 유지, 서버 로그에 예외 종류·상태만 기록. 5xx 1회 재시도 여부는 미결정 |
| 라이선스 확인 중 robots 위반 | git.kernel.org는 모든 자동 요청 금지 | 이후 요청하지 않음, 수집기에 넣지 않음, 기록 |

## 10. 남은 한계

- 게임 ALB 실습("모든 타깃 unhealthy → 503")이 공식 문서의 fail-open 설명과 다르다. 아직 수정하지 않았다.
- 한국어 항목 주석은 사람 검수 전이다. 보조 문서가 없는 항목이 26개라 진단 근거가 얇다.
- 응답 시간은 첫 질문 기준 평균 23~26초다(생성 3회 직렬). 같은 질문은 캐시로 즉시 응답한다.
- 평가는 질문 9개, 개발 도우미 채점이라 사람 검토가 필요하다.
