# F2015 RAG 사용 전후 답변 품질 비교

실행일: 2026-10-21 17시대 · 모델: GMS `gpt-6.1-sol`(양쪽 같음) · 색인: `data/chroma-v2`(지식 100 / 청크 221 + 질문 중 수집 문서)

## 1. 방법

- 질문 9개를 정했다. 문서 안 질문 8개, 문서 밖 질문 1개다. 질문별 정답 기준(핵심 사실)과 근거 절은 **실행 전에** 공식 문서 원문을 읽고 `backend/evaluation/f2015_questions.json`에 고정했다.
- **RAG 없음**: 같은 모델에 질문과 짧은 중립 지시("간결하게 답하고, 확실하지 않으면 모른다고 말한다")만 보냈다. 문서·인용 규칙은 주지 않았다.
- **RAG 있음**: 실제 서비스 경로(`POST /api/chat`)를 그대로 썼다. 검색어 추출 → 후보 선별·수집 → retrieve → generate 순서이며 항목은 질문별로 지정했다.
- 실행 스크립트는 `backend/scripts/compare_rag.py`, 결과 원본은 `docs/submission/evaluation/f2015_results.json`이다(두 답변 전문 포함).
- 채점 기준:
  - 사실 정확성: 정확(핵심 사실 모두) / 부분(일부 누락) / 오답(사실과 다름)
  - 근거 제시: 답변의 주장에 실제 문서 근거가 연결되는가
  - 보류: 근거가 없을 때 모른다고 하는가
- 문서 밖 주장: 우리 색인 문서로 확인할 수 없는 추가 주장이 있는지도 따로 적었다. 이것은 오답이라는 뜻이 아니라 **검증할 수 없다**는 뜻이다.
- **채점자: 개발 도우미(Claude)다. 사람의 검토가 필요하다.** 표본은 9개라서 일반화된 성능 수치로 쓰지 않는다.
- 실행 중 RAG 없음 쪽 Q2가 GMS 502(`generation_request_failed`)로 실패해, Q2만 1회 다시 실행했다(결과 파일에 `retry_note` 기록).

## 2. 요약

| 기준 | RAG 없음 | RAG 있음 |
|---|---|---|
| 사실 정확성(문서 안 8문항) | 정확 7 · 부분 1 · 오답 0 | 정확 6 · 부분 2 · 오답 0 |
| 근거 제시 | 0/8 (출처 없음) | 8/8 (공식 문서 절 인용, 인용 번호 검증 통과) |
| 문서 밖 질문 보류(Q9) | 보류하지 않고 수치로 답함(출처 없음) | "제공된 문서에서 확인되지 않습니다"로 보류 |
| 우리 문서로 확인할 수 없는 추가 주장 | 5/8 문항(Q2·Q3·Q4·Q7·Q8)에 있음 | 0/8(인용한 문서 범위 안에서만 답함) |
| 응답 시간 평균(중앙값) | 11.9초(11.7) | 23.2초(22.7) |

**해석:**
- 이번 모델은 RAG 없이도 잘 알려진 사실 대부분을 맞혔다. **"RAG를 쓰면 정확도가 올라갔다"는 결론은 이 표본으로 내릴 수 없다.**
- RAG의 실제 차이는 세 가지였다.
  1. 모든 주장에 공식 문서 원문 절이 연결되어 사용자가 확인할 수 있다.
  2. 문서 밖 질문(Q9)에 추측하지 않고 보류한다.
  3. 문서로 확인되지 않는 세부(기본값, 변경 가능 여부 등)를 덧붙이지 않는다.
- 대가도 있었다.
  1. 응답 시간이 약 2배다.
  2. 인용 가능한 범위로만 답하다 보니 문서에 있는 조치 일부를 빠뜨렸다(Q2·Q3, 부분).

## 4. 관찰과 설계 반영

1. **근거 제시가 가장 확실한 차이다.** RAG 쪽은 모든 주장에 공식 문서 절 제목과 원문 URL이 붙었고, 인용 번호 검증(F2008)을 통과한 근거만 화면에 남았다. RAG 없음 쪽은 맞는 내용이어도 사용자가 어디서 확인해야 하는지 알 수 없다.
2. **보류 동작이 설계대로 작동했다(Q9).** 같은 모델이 문서 없이는 수치를 단정했다. 인프라 장애 대응에서 확인할 수 없는 수치·정책을 단정하는 것은 위험하다는 기획 근거와 맞는다.
3. **질문 중 외부 후보 검색(F2004)이 실제로 기여했다.** Q5는 `--fail`·`--fail-with-body`, Q7은 errno(3) ENFILE 절을 질문 시점에 새로 수집해 정확도를 끌어올렸다. 미리 연결해 둔 문서만으로는 답할 수 없던 부분이다.
4. **RAG 쪽의 약점: 너무 짧은 답(Q2·Q3).** 근거 문서에 조치가 있는데도 답변 생성 단계에서 생략됐다. → 5절에서 답변 프롬프트를 고친 뒤 같은 질문으로 다시 확인했고, 두 문항 모두 정확해졌다.
5. **비용·지연**: RAG는 질문당 생성 3회(검색어·선별·답변)와 임베딩 1회 이상을 쓰고, 시간이 약 2배다. 같은 질문은 답변 캐시로 0초에 응답한다(앞선 실측).
6. **정확성 비교의 한계**: 이 모델은 curl·Linux·ALB의 공개 지식을 이미 많이 알고 있다. 정확도 차이를 보려면 더 세부적인 문서 조건(예: 덜 알려진 오류 코드, 최신 변경 사항)으로 질문을 늘려야 한다.

## 6. 재현

```powershell
# backend 폴더, 8000 서버 실행 중
.venv/Scripts/python.exe -X utf8 -m scripts.compare_rag
```

같은 질문을 다시 실행하면 RAG 쪽은 답변 캐시가 적중해 시간이 달라진다. 새로 측정하려면 프롬프트 버전 또는 질문을 바꾸거나 캐시 폴더(`data/answers`)를 비운 뒤 실행한다.
